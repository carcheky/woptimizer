# Arquitectura y Separación de Capas (v3)

## Stack Tecnológico
- **Python**: 3.11+
- **Motor de Procesos**: `psutil` (reemplaza cualquier llamada externa a PowerShell o WMI).
- **Persistencia y Validación**: `pydantic v2` para esquemas de datos estructurados.
- **Interfaz Gráfica**: `customtkinter` (modo oscuro por defecto, componentes modernos).
- **Empaquetador**: `PyInstaller` con manifiesto UAC admin.

## Invariante de 3 Capas (Three-Tier Rule)
```
┌───────────────────────────────────────────────┐
│ Capa 1: UI (src/woptimizer/ui/)               │
│ - SOLO CustomTkinter y presentación.          │
│ - NUNCA llama a psutil, subprocess ni JSON.   │
└───────────────────────┬───────────────────────┘
                        ▼ Inyección de dependencias
┌───────────────────────────────────────────────┐
│ Capa 2: Servicios (src/woptimizer/services/)  │
│ - process_service: psutil (listar, matar).    │
│ - pack_service: CRUD de perfiles y packs.     │
│ - gaming_service: reglas y ejecucion del      │
│   Gaming Mode (keepers + categorias).         │
└───────────────────────┬───────────────────────┘
                        ▼ Modelos y Config
┌───────────────────────────────────────────────┐
│ Capa 3: Modelos & Config (src/woptimizer/)    │
│ - models.py: Pydantic schemas (Pack, Info).   │
│ - config.py: Categorías, prioridades, paths.  │
└───────────────────────────────────────────────┘
```

## Reglas de Arquitectura
1. **Kill Recursivo:** Todo cierre de proceso debe usar `parent.children(recursive=True)` antes de matar al padre para evitar procesos huérfanos.
2. **Punto de Entrada Único:** `python -m woptimizer` o `src/woptimizer/__main__.py`. Los servicios se instancian una sola vez y se inyectan en `WOptimizerApp`.

3. **Base de Datos Dinámica:** `assets/process_db.json` actúa como fuente local precargada de forma síncrona en `ProcessService`. Se actualiza de forma asíncrona desde el repositorio oficial en GitLab sin bloquear la GUI.
4. **Residencia en Bandeja (System Tray):** La aplicación no finaliza al presionar `[X]`; intercepta `WM_DELETE_WINDOW` para ocultarse (`withdraw`) y levantar un icono en la barra de tareas mediante `pystray`. Solo la opción 'Salir' destruye el proceso.
5. **Telemetría de RAM y Logs:** Las rutinas de finalización (`kill_processes` y `kill_pack_apps` en `ProcessService`) calculan la memoria física liberada (`proc.memory_info().rss`) de cada proceso y sus hijos antes del cierre. Retornan una 4-tupla estructurada: `(killed: int, failed: int, skipped: int, freed_mb: float)`. Solo se contabilizan los bytes liberados en procesos efectivamente terminados. Errores de acceso (`AccessDenied`) y avisos del backend se canalizan a `woptimizer.log`.
6. **Entornos de Sincronización en la Nube (Nextcloud/OneDrive):** En Windows con unidades virtuales (VFS), los archivos `.git` pueden marcarse como reparse points y quedar corruptos (`fatal: bad object HEAD`). Para operaciones de Git locales se recomienda aislar el repositorio o redirigir `$env:GIT_DIR`. El versionado pasa SIEMPRE por `python .taskmaster/git_safe_commit.py "..."`, cuyo código de salida es un contrato normativo (`0` commit creado o nada que comitear, `1` fallo de git, `2` uso incorrecto, `3` repositorio no verificable) documentado en [`sandbox-rules.md`](sandbox-rules.md); `--verify` valida el repositorio sin escribir nada.
7. **Cache y Rendimiento en ProcessService (TASK-018):**
   - **Hashmap O(1):** La base de datos de procesos (`_db_map`) se almacena como `dict[str, tuple]` en lugar de una lista de Pydantic models. Lookup exacto en O(1), con fallback a fuzzy match.
   - **Meta-cache memoizado:** Las correspondencias fuzzy se guardan en `_meta_cache` para no repetir búsquedas (cubre ~130 procesos únicos por sesión).
   - **Cache TTL (2s):** `get_running_processes()` retorna un snapshot cacheado si se llama de nuevo dentro de 2 segundos. Pasar `force_refresh=True` ignora el cache. Las operaciones de kill invalidan el cache automáticamente.
   - **Impacto:** Lectura cacheada en ~0.003 ms vs ~15 ms del cold scan (~5000x speedup). Permite a la UI hacer refresh agresivo sin penalización.
   - **Propiedad `process_db`:** Existe como `@property` de compatibilidad que reconstruye la lista de `ProcessInfo` bajo demanda desde `_db_map`.
8. **Notificaciones Nativas del Sistema (TASK-019):**
   - `NotificationService` (`src/woptimizer/services/notification_service.py`) envuelve `pystray.Icon.notify()` para emitir toasts/balloons nativos de Windows. **No es una dependencia nueva**: reutiliza `pystray`, ya presente por TASK-012.
   - **La UI nunca importa `pystray` directamente.** Las vistas reciben el servicio por inyección (ver `ui-design-system.md`) y solo consumen la API `notify_kill_result()`, `notify_pack_activated()` y `notify_apps_launched()`.
   - **Ciclo de vida del icono:** `WOptimizerApp.show_tray()` llama `attach_tray(icon)` tras crear el icono; `show_action()` llama `detach_tray()` al restaurar la ventana. El intercambio de la referencia está protegido por `threading.Lock`.
   - **Degradación segura:** `notify()` **nunca propaga excepciones**. Sin bandeja adjunta registra en el log y retorna `False`; si el backend lanza, captura y registra `warning`. También consulta `Icon.HAS_NOTIFICATION` para no llamar a backends que no soporten la API.
   - **Autostart del tray:** el icono se levanta en `WOptimizerApp.__init__` (no solo al cerrar la ventana) para que las notificaciones funcionen con la ventana visible. Se puede desactivar con `autostart_tray=False` (lo usan los tests headless). `show_tray()` es **idempotente** mediante un guard, porque se invoca desde dos puntos.
   - **Dependencias declaradas:** `pystray` y `Pillow` están en `pyproject.toml` para que PyInstaller las empaquete.
9. **Invariante Crítico: Emojis de Categoría (TASK-020):**
   - **Regla:** los emojis de categoría de `PROCESS_CATEGORIES` (`config.py`) deben coincidir **exactamente, carácter a carácter**, con los usados en `assets/process_db.json` y con el sistema de diseño de `ui-design-system.md`.
     - `🟢 SEGURO` → Navegadores, Sincronización, Productividad
     - `🟡 PRECAUCIÓN` → Chat, Media, Launchers Gaming
     - `🔴 NO CERRAR` → Sistema de Windows, Antivirus, Overlays e Info
   - **Por qué importa:** el lookup de categoría compara strings exactos. Un emoji distinto (p. ej. `🔴 Navegadores` en `config.py` vs `🟢 Navegadores` en el JSON) hace que **todas** las entradas de esa categoría caigan en `⚪ Otros`, perdiendo su semáforo de seguridad.
   - **Bug corregido:** `config.py` tenía `🔴` en navegadores/sincronización y `🟢` en overlays, invertido frente al JSON. 6 de 8 categorías estaban huérfanas.
   - **El centinela `⚪ Otros` tiene una sola fuente de verdad (TASK-026 / FIX-005):** `CATEGORY_ORDER[-1]` en `config.py:95` y el default de `ProcessInfo.category` en `models.py:9`. El fallback del servicio (`process_service._DEFAULT_META` y el `props.get('category', ...)` de `_load_local_db`) usaba `"? Otros"` (ASCII U+003F), que **no** es el círculo U+26AA: ese proceso caía fuera de `CATEGORY_ORDER` y se ordenaba con el centinela `999` de `result.sort(key=lambda p: cat_idx.get(p.category, 999))`. Y el filtro del acordeón de `pack_manager_view.py` comparaba contra el mismo literal equivocado, con lo que dejaba de excluir la categoría canónica de `target_categories`. **Los tres sitios cambian juntos**; arreglar solo dos deja un no-op inofensivo que se vuelve basura seleccionable.
   - **Prioridad de evaluación en `get_safety_badge()`:** la **categoría manda sobre la prioridad**. Antes `priority in [medium, low]` se evaluaba antes que el emoji de categoría, así que una categoría 🔴 con prioridad `low` se pintaba 🟡 PRECAUCIÓN. Ahora: (1) emoji de categoría, (2) palabras clave, (3) prioridad como desempate.
   - **Test de regresión:** `test_category_emoji_alignment` falla si alguna categoría del JSON no existe en `config.py`. `test_safety_badge_category_priority_order` cubre el orden de ramas.
10. **Invariante Crítico: Aislamiento de Listas del Pack Gaming (TASK-021 + TASK-026/FIX-001):**

   - **Deuda latente cerrada (TASK-026 / FIX-001):** el fallback de `get_gaming_pack()` tenía el mismo `model_copy()` shallow. **No era alcanzable** (`get_gaming_pack()` no tiene llamadores en la UI: todo pasa por `get_all_packs()`, y `_ensure_gaming_pack()` siempre inserta la clave `"gaming"`), así que un solo llamador futuro bastaba para reintroducir la contaminación.
   - **Test de regresión:** `test_gaming_pack_lists_isolated_from_global` (ciclo #10) comprueba la identidad de objeto (`is not`) con la clave **presente**. `test_gaming_pack_fallback_is_deep_copy` (TASK-026) hace `del svc._data.packs["gaming"]` para **forzar el fallback**, que era la única ruta sin cobertura, y comprueba además `keepers`.
11. **Runtime del Gaming Mode: `GamingService.execute_gaming_pack` (TASK-025 / FIX-002 + FIX-008):**
   - **Por qué en `gaming_service` y no en `process_service`:** `ProcessService` es el adaptador de `psutil`; meter la política de Gaming Mode ahí obligaría a la capa de sistema a conocer el modelo `Pack`. `GamingService` ya existía como dueño de `should_kill_for_gaming`, así que **añadir un método a `ProcessService` crearía dos fuentes de verdad** para el orden de las reglas.
   - **Contrato:** `execute_gaming_pack(gaming_pack: Pack) -> Tuple[int, int, int, float]`, es decir `(killed, failed, skipped, freed_mb)`, **la misma 4-tupla** que `kill_processes` / `kill_pack_apps`. Así el banner de la portada y los toasts no cambian de contrato. `is_gaming is False` → `ValueError` (uso indebido).
   - **Rutas de entrada:** las **tres** (menú del tray, `DashboardView.execute_pack` y `PackManagerView.kill_pack`) llaman a `execute_gaming_pack` cuando `pack.is_gaming`. `kill_pack_apps` queda **solo** para packs de usuario. `MainWindow._show_home` / `_show_packs` inyectan `self.gaming_service` como 5.° argumento, y ambas vistas aceptan `gaming_service=None` con fallback `GamingService(process_service, pack_service)` (mismo patrón defensivo que `notification_service`), para no romper constructores antiguos ni tests.
   - **Orden de reglas (normativo, G0-G9):** `G0` snapshot con `force_refresh=True` (la cache tiene TTL de 2 s y la doble pulsación tarda ~0,4 s: sin forzar se quedan fuera procesos recién lanzados — es eficacia, no seguridad) → `G1` barrera de categoría roja sobre `target_categories` → `G2` recorrido → `G3` **el nombre se evalúa siempre contra `p.full_name or p.name`** → `G4` blindaje de nombres (`is_system_protected`) → `G5` barrera de categoría roja sobre la categoría del proceso → `G6` keepers > apps > categorías → `G7` candidatos → `G8` única llamada a `kill_processes` → `G9` `skipped` **suma** los descartes del filtro a los de la vía de kill, para que la UI vea lo protegido en vez de silenciarlo.
   - **G-3 (`full_name`, nunca `name`):** los keepers y las apps explícitas se guardan con extensión (`"discord.exe"`, `"chrome.exe"`) mientras que `ProcessInfo.name` llega sin ella (`"discord"`). El matching de `should_kill_for_gaming` es por subcadena, así que evaluar con `name` haría que **keepers y apps murieran en silencio**: el usuario configuraría Steam y Discord como keepers y ambos caerían.
   - **G-2, barrera de categoría roja (la garantía anti-brick):** una categoría `🔴` en `target_categories` es **inerte, sea cual sea el nombre**, y se aplica en **dos sitios independientes**: (1) `get_safety_badge(c)["tier"] == "danger"` filtra `target_categories` antes de evaluar, y (2) un segundo filtro sobre `p.category` del snapshot. Hace falta porque `svchost` y `explorer` están en `🔴 Sistema de Windows` en `assets/process_db.json` y **no** figuran en `SYSTEM_PROTECTED_PROCESSES` (`is_system_protected('svchost')` es `False`): la categoría roja se ofrece como casilla activable en el acordeón del Gestor de Packs, y matarla dejaría Windows inservible. El blacklist de nombres no es una garantía suficiente para una evaluación por categoría, porque depende de que alguien se acuerde de añadir cada nombre nuevo.
     - ⚠️ **Corrección TASK-028 (esta frase citaba el fichero equivocado, y el error era de los que hacen perder tiempo).** Este documento situaba `SYSTEM_PROTECTED_PROCESSES` en **`config.py`**. **Es falso: vive en `src/woptimizer/services/process_service.py:33-48`** (un `frozenset` de 34 nombres), junto al adaptador de `psutil` que lo consume, y **no** en `config.py` (que solo tiene `PROCESS_CATEGORIES` y los `patterns` legacy de clasificación). Importa porque quien vaya a tocar el blindaje irá primero a `config.py` y no lo encontrará, y porque `PROCESS_CATEGORIES['🔴 Sistema de Windows']['patterns']` (`config.py:82-86`) es una lista **distinta**, más amplia y de otro propósito: incluye procesos del usuario (`taskmgr`, `cmd`, `powershell`, `wsl`) que no rompen el SO. No son intercambiables. Verificado en caliente: `svchost` y `explorer` **no** están en el `frozenset` (`is_system_protected('svchost')` → `False`), que es lo que hace necesaria la barrera de categoría de arriba. Los 34 nombres están transcritos y explicados en [`data-models.md`](data-models.md), sección 'Blindaje anti-brick'.
     - *(El encargo de TASK-028 citaba `process_service.py:23-38`; el rango real del `frozenset` es **33-48**, medido con `ast`. Aquí se transcribe el rango medido, no elAuditado.)*
   - **G-1, una sola puerta de kill:** `gaming_service.py` **no** importa el adaptador de procesos ni el de disco; delega íntegro en `kill_processes`, que ya aplica el blindaje de nombres, el kill recursivo (hijos antes que padre) y `invalidate_cache()`. El módulo **no** reimplementa el bucle de kill ni añade una cuarta llamada a un método privado de otro servicio.
   - **Gaming Mode sin apps:** un Gaming Mode válido puede tener `apps` vacía, porque su configuración vive en `keepers` + `target_categories`. Los dos `if not pack.apps: return` mudos de `dashboard_view.py` y `pack_manager_view.py` se levantaron a `if not pack.is_gaming and not pack.apps`, o el Gaming Mode solo por categorías no se ejecutaría nunca.
   - **Threading:** el kill va en `threading.Thread(..., daemon=True)`. La UI solo se toca con `self.after(0, ...)`, nunca `self.master.after(...)` (`MainWindow` destruye la vista en toda navegación y `master` es `content_frame`, que sobrevive). En el tray no hay `after`: solo `logger` + `notification_service`, ambos seguros desde cualquier hilo.
   - **Test de regresión:** `test_execute_gaming_pack_integration` (en `run_tests.py`) tiene una capa A con un doble que captura la lista que llega a `kill_processes` (sin matar nada del sistema: `svchost` con su categoría roja marcada debe quedar fuera y `discord` protegido por su keeper), una capa B que verifica el kill recursivo real contra un sleeper espawneado, y un sub-chequeo estático con `_codigo_ejecutable` que congela la separación de capas.
12. **Invariante Crítico: el estado de una vista se publica solo desde el hilo principal (TASK-026 / FIX-007):**
   - **Regla:** un hilo de trabajo **solo calcula**; publica Calling `self.after(0, _apply)` y dentro de `_apply` se asignan `self.processes` y `self.grouped_processes` y se redibuja. Nunca se muta en sitio un dict que el hilo principal itera, y nunca `self.master.after(...)` (`MainWindow` destruye la vista en toda navegación y `master` es `content_frame`, que sobrevive: un `after` colgado ahí reconfigura widgets ya destruidos, el bug que cerró TASK-023).
   - **Por qué importa:** el hilo principal recorre `grouped_processes` en `_render_list` (también en **cada pulsación** del buscador, por el trace de `search_var`) mientras el secundario hacía `.clear()` y `[k] = []` sobre ese mismo dict. Tres fallos distintos: (a) `RuntimeError: dictionary changed size during iteration`, que sube por el trace de la variable de Tk y **tumba la app**; (b) con dos cargas solapadas, `processes` y `grouped_processes` describían snapshots distintos; (c) `on_kill_selected` (`:263`) leía `grouped_processes` para matar: un agrupado a medio aplicar puede salir **vacío con casillas marcadas** o contener PIDs de un snapshot obsoleto. Este producto mata procesos reales de Windows, así que (c) es un riesgo de seguridad, no de UX.
   - **Rebind, no mutación:** el agrupado se entrega como dict **nuevo** (`ProcessManagerView._group(procs)`, una función pura y estática, testeable sin Tk) y se REBINDea en el hilo principal. `_render_list` toma además un snapshot local (`grouped = self.grouped_processes`) para que un render lea un único estado coherente de principio a fin.
   - **Ojo con `tkinter`:** `after` desde un hilo secundario lanza `RuntimeError: main thread is not in main loop` si el principal no está dentro del bucle de eventos. En la app no pasa porque las vistas se construyen y se invocan desde handlers (ya dentro del mainloop); en los tests, o se usa el mainloop de verdad, o —como hace el arnés sin Tk de `test_do_load_publica_sin_tk`— ni se abre ventana: un `after` falso que encola y el test como bucle de eventos. Nunca un bucle con `update()` + `sleep`.
   - **Test de regresión:** `test_do_load_publica_sin_tk` (en `run_tests.py`, antes `test_process_manager_view_publishes_on_main_thread`) cubre cuatro capas: (A) `processes` y `grouped_processes` son **propiedades que anotan `threading.get_ident()`**, así que ninguna publicación puede venir del secundario; el agrupado se guarda en un `RecordingDict`, de modo que una mutación in situ también queda con su hilo; (B) dos `_do_load` solapados con snapshots distintos acaban con `grouped_processes == _group(processes)`; (C) el camino de crash se reproduce **sin azar** (la dict se queda parada en la primera mutación, el lector abre el iterador y lo sigue recorriendo) y (D) una guarda `ast` que se ejecuta **primero, sin Tk**, y falla en <1 s con un mensaje limpio si alguien reintroduce la regresión.
   - **El arnés NO abre ventana (TASK-030).** La vista se construye con `__new__` (sin `CTk.__init__`), el `after` de la vista **encola** el callback y el propio test hace de bucle de eventos: `join(10)` al hilo secundario y ejecución en el principal de lo entregado. Sin `CTk`/`root`/`mainloop` no existe ruta por la que Tcl pueda colgarse, así que **el watchdog de `faulthandler` (150 s, `exit=True`) se eliminó**: mataba el runner entero y con él todos los tests posteriores. La guarda `ast` se conserva y deja de ser la única red.
13. **Invariante Crítico: `load()` es de SOLO LECTURA y hay UNA puerta de "legible" (TASK-031):**
   - **Regla 1 — una sola definición de "el fichero es sano":** `_es_legible(path)` = `try: self._read_json(path) → True / except CORRUPTION_ERRORS: False`. La usa `_rotate_backup()` **y** nada más la reimplementa. Antes el fichero tenía **dos** definiciones (`load()` por `_read_json`, `_rotate_backup()` por `json.load`) y el docstring describía la que no se ejecutaba: un `{"name": 7}` es JSON válido, así que la rotación lo daba por sano y **copiaba el principal corrupto encima del `.bak` bueno**. `OSError` se deja fuera a propósito (no es corrupción y debe propagar).
   - **Regla 2 — el arranque no escribe:** `load()` no llama a `save()` por ninguna ruta, y `_ensure_gaming_pack()` asegura el pack `gaming` **en memoria**. El pack se persiste en el primer `save()` real. Verificado por grep antes de cambiarlo: `PROFILES_FILE` (`config.py:26`) tiene **un solo** consumidor, `PackService.__init__`, y `get_gaming_pack()` cae a `DEFAULT_GAMING_PACK.model_copy(deep=True)`, así que la app funciona sin fichero.
   - **Regla 3 — sin `.bak` legible no se regenera nada:** se carga lo legible, se marca `fichero_danado` y el fichero **se queda en disco tal cual**. La pérdida pasa de irreversible a reversible. El pack `gaming` en memoria permite arrancar igual.
   - **Regla 4 — las dos ramas de parseo pasan por el modelo:** la moderna con `AppData(**raw_data)` y la legacy traduciendo el registro a un `dict` moderno antes de `Pack(**traducido)`. La legacy antes construía el `Pack` con una lista de campos escrita a mano (**5 de 8**) y por eso `keepers` —la lista **anti-brick** del Gaming Mode— y `target_categories` no se leían nunca. En cuanto `Pack` gane un campo, ambas lo leerán sin que nadie se acuerde.
   - **Por qué importa (seguridad, no-Heurística):** `keepers` es la lista de procesos **protegidos** (`gaming_service.py:24`). Cargar un `keepers: "steam.exe"` "con lo que hay" solo tiene una forma: normalizar a `[]`, y eso **borra** la protección en el primer `save()`, sin aviso, y el Gaming Mode mata lo que debía proteger. Por eso una hoja mal formada es **corrupción** y no un pack con un campo raro. El criterio entero y sus tres condiciones están en [`data-models.md` §4.4](data-models.md).
   - **Estado observable, no silencio:** `PackService` expone `fichero_danado`, `recuperado_de_backup`, `motivo_danado` y `mensaje_danado() -> Optional[str]`. El estado vive en el **servicio** (la UI no lee ficheros ni decide); pintarlo en el `status_label` es de la capa de UI y sigue pendiente.
   - **Tests de regresión:** sondas **L1–L7** en `run_tests.py` (36 → 43), cada una con su mutación verificada morriendo sobre una copia de `src/`: `L1` rotación, `L2` clasificación de la hoja y texto del mensaje, `L3` `load()` no escribe, `L4` recuperar no refresca el `.bak`, `L5` sin `.bak` no se reescribe el principal, `L6` campo desconocido, `L7` `packs` + `profiles`. Tabla y por qué existe cada una en [`testing-guide.md`](testing-guide.md).

14. **Invariante Crítico: arrancar una app NO es ejecutar un comando (TASK-027 / FIX-003):**
   - **Regla:** `ProcessService._resolver_app()` es una **función de decisión pura** (devuelve la ruta ABSOLUTA validada o `None`) separada del efecto (`_lanzar()`). `start_pack_apps()` solo recorre, cuenta y loguea. La entrada es `Pack.apps`, de `profiles.json`: un fichero que el usuario edita a mano y que este producto está pensado para compartir, así que **el pack es entrada no confiable** (mismo argumento que el blindaje anti-brick de TASK-024, aplicado al arranque).
   - **El orden de las reglas ES la seguridad** y no se reordena: (1) entrada no vacía sin `\x00` → (2) **rechazo UNC** → (3) nombre pelado buscado **solo** dentro de las raíces permitidas → (4) `normpath` → (5) **contención léxica** → (6) **extensión léxica** en `.exe`/`.com` → (7) `isfile` → (8) **resolución real** (`_ruta_real`, fail-closed) + **contención real** + **extensión real** → (9) **el fichero es una imagen PE** (`_es_imagen_pe`, fail-closed) → (10) se devuelve la **ruta real**. La regla 8 es la corrección de la iteración 2 (abajo) y **no se puede reordenar**: `isfile` va antes porque, si no, el motivo que se registra para un nombre mal escrito sería "no se pudo resolver" en vez de "no existe", y el usuario edita su `profiles.json` a mano.
   - **Por qué `shell=False` no era el arreglo (medido antes de escribir el código):** con `shell=False`, `CreateProcess` busca el **CWD antes que el PATH**, así que un `chrome.exe` soltado junto a `woptimizer.exe` se ejecutaría en lugar del Chrome real (`os.path.isfile("cmd")` → `False`, pero `shutil.which("cmd")` → `C:\WINDOWS\system32\cmd.EXE`). Por eso **no se resuelve con `shutil.which()`**: buscar en el PATH es buscar en el CWD.
   - **Por qué `os.startfile` tampoco lo era solo:** delega en `ShellExecute`, que **sí** ejecuta `.bat`/`.cmd`/`.ps1`/`.vbs` por su intérprete. Cambiar `Popen(shell=True)` por `startfile` sin lista blanca de extensiones sería cambiar de hugging por ahorcamiento. De ahí `_ALLOWED_APP_EXTS = {".exe", ".com"}`.
   - **Por qué `isabs` no vale y la contención va DESPUÉS de normalizar:** `isabs` da `True` para `C:\Program Files\..\..\Windows\System32\cmd.exe` (traversal) y para `\\servidor\comparte\p.exe` (ejecución remota por SMB). Y `commonpath()` sobre la ruta **cruda** también pasa el filtro (medido: `commonpath([cruda, 'C:\Program Files']) == 'C:\Program Files'`). Si la contención se comprueba antes de `normpath`, el traversal pasa las dos comprobaciones.
   - **La contención léxica NO era suficiente: un junction la atraviesa (corregido en la iteración 2 de TASK-027).** La afirmación anterior de este §14 —"solo se arranca lo que está bajo las raíces permitidas"— era **falsa** para un enlace de directorio. Medido en esta máquina, con un junction de verdad (`mklink /J <TEMP>\jdir C:\Windows\System32`):

     | comprobación | resultado sobre `<TEMP>\jdir\cmd.exe` |
     |---|---|
     | `os.path.normpath` | `<TEMP>\jdir\cmd.exe` (intacta: es **léxica**) |
     | `os.path.commonpath([ruta, %LOCALAPPDATA%])` | `%LOCALAPPDATA%` → "contiene": **falso** |
     | `os.path.isfile(ruta)` | `True` (sigue el enlace) |
     | `os.stat(ruta).st_file_attributes` | `0x20` — **ni reparse**: el atributo tampoco lo ve |
     | `os.path.realpath(ruta)` | `C:\Windows\System32\cmd.exe` ← la verdad |

     Es decir: el junction se aceptaba y `cmd.exe` arrancaba. **La arreglo es la regla 8:** resolver la ruta por descriptor y repetir las dos comprobaciones sobre la ruta real. En Windows eso es exactamente lo que hace `os.path.realpath(..., strict=True)` (por debajo, `GetFinalPathNameByHandleW`; medido también con un enlace de **fichero**), así que **no hace falta `ctypes`**: mismo resultado, menos código que mantener. **Fail-closed:** si el SO no resuelve la ruta, `_ruta_real` devuelve `None` y **no se arranca**. Las **raíces** se resuelven por el mismo camino, o un junction en algún tramo de `%LOCALAPPDATA%` rechazaría apps legítimas (el otro modo de fallar).
   - **La extensión se comprueba en el alias Y en el destino.** Un `.exe` que es un enlace a un `.bat` **de una raíz permitida** pasa la contención real, y sin mirar la extensión del destino la lista blanca se esquiva entera (y `ShellExecute` lo pasa por `cmd.exe /c`). El `.bat` de destino es un fichero legítimo de una raíz: esto no es un junction fuera, es la lista blanca por un hueco.
   - **`commonpath` normaliza con caja, y en Windows el sistema de ficheros no.** Medido: `commonpath(['C:\PROGRAM FILES\x.exe', 'C:\Program Files'])` devuelve `'C:\PROGRAM FILES'`, que no es la raíz, así que `C:\PROGRAM FILES\...` se rechazaba. Eso era fail-closed (seguro) pero un **bug funcional**: un programa legítimamente instalado con otra caja no arrancaba nunca. **Decisión: se normaliza con `os.path.normcase` en los dos lados**, y no se documenta como limitación. El argumento para hacerlo es que `normcase` **no ensancha** el conjunto aceptado: declara la verdad del SO, de modo que lo que entra es exactamente lo que el SO abriría; y la contención y la extensión **reales** siguen aplicando encima. `normcase` tampoco sustituye a `commonpath`: un `startswith` abriría el hermano de prefijo (`...\Temp\wopt_x` aceptaría `...\Temp\wopt_xEvil\a.exe`), y eso lo vigila `test_la_contencion_no_acepta_un_hermano_de_prefijo`.
   - **No se blacklistean metacarácteres** (`& | ; > < ^`): `C:\Program Files\Rock & Roll\game.exe` es una ruta legítima y un filtro de metacarácteres rechaza apps reales de Steam y de itch.io. Sin intérprete no hay metacarácteres que escapar: la validación es **estructural**, nunca de caracteres. Y **no se pasa ningún argumento**, así que tampoco se puede colar uno.
   - **Raíces permitidas** (fail-closed): `%ProgramFiles%`, `%ProgramFiles(x86)%`, `%ProgramW6432%`, `%LOCALAPPDATA%`, `%APPDATA%`, `%ProgramData%`; las que no existan se descartan y, si no queda ninguna, **no se arranca nada**.
   - **Honestidad sobre el modelo de amenaza:** esta lista de raíces **NO es un sandbox** — `%APPDATA%` y `%LOCALAPPDATA%` son escribibles por el usuario, así que un atacante local con escritura en disco pasa por aquí. Lo que sí cierra es hygiene con criterio: nada por intérprete, nada desde una compartición remota, nada por traversal, nada por junction o symlink, nada que no sea una imagen PE, ningún argumento. Prometer más sería falso.
   - **El hard link: la deuda anterior estaba mal fundada, y está CERRADA (iteración 3 de TASK-027).** Este §14 decía antes que un **hard link** (`mklink /H`) "no es un reparse point, así que ni `realpath` ni los atributos lo ven" y que "no hace falta cerrarlo". **Las dos mitades de esa razón son falsas**, y la segunda es la que importa:
     - **"Ningún filtro lo ve" es falso.** `os.stat(ruta).st_nlink` vale **2** en un hard link (medido). Sí lo ve.
     - **Y da igual que lo vea: el hard link no era el agujero.** Medido en esta máquina con las dos variantes construidas de verdad, `_resolver_app` acepta el hard link (`alias.exe` → `payload.bat` fuera de las raíces, `st_nlink == 2`) **y también una COPIA PLENA** del mismo `.bat` con nombre `.exe` (`st_nlink == 1`, sin un solo enlace, sin junction, sin symlink y sin privilegios). Rechazar `st_nlink > 1` habría cerrado el caso exótico y habría dejado abierto el trivial: seguridad de teatro.
     - **La otra variante que se ofreció —"rechazar solo si el destino no está en las raíces"— no es implementable.** Un hard link no tiene destino consultable: no existe API en Windows que devuelva los otros nombres de un fichero a partir de su ruta. Y aunque la hubiera, sería irrelevante, porque el atacante elige qué nombre queda dentro de la raíz.
     - **Lo que sí cierra las dos (y las de cualquier otro tipo) es la regla 9, `_es_imagen_pe`:** la lista blanca de `.exe`/`.com` siempre quiso expresar que *`.exe` significa "imagen PE", no "algo que se arranca"*, pero se cumplía mirando el **nombre**. La regla 9 comprueba el **contenido** (`MZ` + la firma `PE\0\0` en el offset que declara `e_lfanew`), después de la resolución real, sobre el fichero que se va a arrancar de verdad. Fail-closed: lo que no se puede leer no es un PE y no se arranca.
     - **El coste, medido antes de escribirla (por qué no rompe nada de verdad):** de **2273** `.exe`/`.com` instalados en las seis raíces, **2200** llevan `MZ` + `PE\0\0`, y **ninguno de los 189 que tienen `st_nlink > 1` falla** (0 falsos negativos en precisamente el caso que se quería cerrar). Los 19 sin cabecera son appx de WindowsApps, la caché de MSI de `%APPDATA%\Microsoft\Installer` y un `.COM` DOS de 16 bits: ninguno es una app lanzable. Los `.com` de verdad (LibreOffice, WinSCP) **sí** son PE.
     - **Por qué no se usa `st_nlink`, en una frase:** porque **el 8,32 % de los ejecutables instalados tienen enlaces duros legítimos** (`msinfo32.exe`, `TabTip.exe`, los auxiliares de Edge con `st_nlink == 6`, las herramientas de Hyper-V). Rechazar "cualquier `st_nlink > 1`" es un falso positivo del 8 % sobre software real, y el control (6) de `test_un_hard_link_no_es_una_hoja_y_el_script_no_pasa` lo impide para que nadie lo vuelva a intentar.
   - **Consecuencia de la regla 8 que hay que decir en voz alta: una biblioteca en un junction a OTRA unidad deja de arrancar.** Si `%LOCALAPPDATA%\Juegos` es un junction a `D:\Juegos`, `realpath` devuelve `D:\Juegos\…`, que no está en ninguna raíz permitida, así que la app **se rechaza**. Es el comportamiento correcto según la política (la política es "estas raíces", y `D:\` no es una de ellas; aceptar cualquier destino resolvero equivaldría a no comprobar nada), pero es un cambio observable para un usuario que tenga la biblioteca en otra unidad. Lo que evita que sea un fallo mudo es el log: nombra el junction y **las dos** rutas (`…\Juegos\juego.exe -> D:\Juegos\juego.exe`). Si en algún momento hay que admitir más destinos, se añaden raíces, no se relaja la comprobación.
   - **El contador `(started, failed)` es un contrato, no un detalle:** con `shell=True` un nombre inexistente **no lanza excepción** (`cmd.exe` responde "no se reconoce como un comando" con código de salida 1), así que el `except` de antes nunca se disparaba y `started` contaba apps que no arrancaron: el toast de éxito mentía en verde. `started += 1` va **después** del `try`, y un rechazo de validación cuenta como `failed` **con su motivo en el log** (el usuario edita su `profiles.json` a mano y sin log no puede depurar por qué su app no arrancó).
   - **La UI guarda la RUTA, no el nombre:** `on_add_to_pack` persiste `procs[0].exe_path` (ya relleno en `get_running_processes()`) y degrada a `full_name` cuando `psutil` no puede dar el `exe` (`AccessDenied`). Sin esa degradación, un proceso sin `exe` deja el pack inservible sin explicación.
   - **Tests de regresión:** `test_arranque_de_apps_no_usa_shell` (sin Tk, sin DB, con `os.startfile` y `subprocess.Popen` instrumentados — el `Popen` sembrado lanza `BaseException`, no `Exception`, para que el `except Exception` del código viejo no lo pueda digerir en verde), `test_el_gestor_guarda_la_ruta_absoluta` y, de la iteración 2, `test_un_junction_no_puede_colar_lo_que_hay_detras`, `test_la_contencion_no_acepta_un_hermano_de_prefijo`, `test_la_contencion_no_depende_de_la_caja` y `test_la_guarda_de_shell_true_ve_atributos_y_aliases`; de la iteración 3, `test_un_hard_link_no_es_una_hoja_y_el_script_no_pasa` (hard link real, copia plena, `MZ` sin `PE\0\0`, `e_lfanew` absurdo, fail-closed y el control (6) sobre un `.exe` **instalado** con `st_nlink > 1`). 15. **Invariante: el canal de log se DECLARA, no se hereda de importar (TASK-028 / FIX-010):**
   - **La regla.** Existe `setup_logging()` en `config.py` y la invoca **quien quiera
     tener log a fichero**: `__main__.main()` antes de instanciar los servicios, y
     `run_tests.py` en su `__main__`. **`config.py` no configura nada al importarse.**
   - **Por qué NO se puede dejar como estaba.** Antes `config.py` ejecutaba
     `logging.basicConfig(...)` a **nivel de módulo**: el contrato de §5 ("los errores
     se canalizan a `woptimizer.log`") se cumplía como **efecto colateral de importar**.
     Eso se rompe en silencio en cuanto alguien importa el paquete sin pasar por
     `__main__`, y el caso real no es hipotético: **`run_tests.py` importa los
     servicios sin pasar por ahí**. Sin fichero, un `logger.warning` no se pierde:
     lo recoge el `lastResort` de la stdlib y sale por **stderr**, que es un fallo
     mudo (parece un aviso del script y es la configuración del producto).
   - **`force=True` es obligatorio, no cosmético.** `logging.basicConfig()` es un
     **no-op mudo** si el root ya tiene handlers. Sin `force`, la segunda llamada no
     reinstala el fichero, un handler ajeno sobrevive y sus avisos se siguen yendo a
     donde se fueran. Con `force=True` la llamada es **idempotente por construcción**:
     cierra y quita lo anterior y deja exactamente un handler.
   - **El log rota.** `RotatingFileHandler` con `maxBytes = 1 MiB` y `backupCount = 3`.
     El destino y el formato **no cambian** (mismo `woptimizer.log`, mismo
     `'%(asctime)s - %(name)s - %(levelname)s - %(message)s'`), solo deja de crecer
     sin control: el fichero había llegado a **1.799.880 bytes (1,8 MB)**, casi todo
     ruido de la propia suite. Ojo al ignorar eso: `.gitignore` tenía `*.log`, que
     **no** casa con `woptimizer.log.1`; sin la línea `*.log.*` un `git add -A` se
     lleva por delante el histórico rotado.
   - **`logger` no se mueve.** `logging.getLogger('woptimizer')` sigue en `config.py`
     y lo importan `notification_service.py:21`, `pack_service.py:8`,
     `process_service.py:7` y `ui/app.py:41,90`. Es el punto de contrato; desacoplar
     el *canal* no toca el *nombre*.
   - **Test de regresión:** `test_logging_va_a_fichero_y_no_a_stderr` (TASK-028). No
     se limita a comprobar que existe un `FileHandler` —eso también lo daría un
     `getLogger()` cualquiera—: afirma sobre el **contenido** (la marca del aviso
     aparece dentro de `woptimizer.log`) y sobre el **control negativo** (la misma
     marca **no** aparece en `stderr` con `contextlib.redirect_stderr`). La segunda
     mitad es la que mata la implementación sin `force=True`: siembra un `StreamHandler`
     a stderr, vuelve a llamar a `setup_logging()` y mira si el aviso se escapa.
